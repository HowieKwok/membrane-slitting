# 编译与终端环境说明

本文件记录本仓库（`Mef_VisionFrame.sln`，激光模切裁切一体机视觉框架）的编译方式、
工程文件约定，以及 2026-10 排查过的两类环境问题。给接手的人看，避免重复踩坑。

## 1. 环境基线

| 项 | 要求 |
|---|---|
| 目标框架 | .NET Framework 4.7.2（全部工程） |
| 编译器 | Visual Studio 2026（本机安装在 `C:\Program Files\Microsoft Visual Studio\18\Community`） |
| 平台 | x64。Halcon 引用的是 `halcondotnetxl`（x64 版），主程序 `Prefer32Bit=false` |
| 视觉库 | Halcon 20.11（`halcondotnetxl` / `halconxl`） |
| 硬件 SDK | 相机/光源厂商 DLL 统一放在仓库 `DLL\CamDLL`、`DLL\LightDLL`；HslCommunication、log4net 等在 `Frame_Core\DLL` |
| 运行目录 | 生产数据/日志硬编码 `E:\生产数据\`、`E:\日志文件\`、`E:\点检数据\`，没有 E 盘会在运行期陆续报错 |

## 2. 一键编译

```bat
build_debug.bat            :: Debug | Any CPU 增量编译
build_debug.bat rebuild    :: 清理后全量编译
```

- 脚本用 `vswhere` 自动找到已安装的 VS，不会因为 VS 版本/安装路径不同而失效。
- 日志写到仓库根目录 `build_debug.log`（UTF-8），出错时直接搜 `error CSxxxx` / `error MSBxxxx`。
- 当前基线：**0 个错误**，约 850 条警告（基本是"字段未使用/过时 API"，不影响构建）。

## 3. 2026-10 修复的工程文件问题（"Debug 编不过"的真正原因）

现象：Release 能过，Debug 报 242 条错误，主要是 `CS0227 不安全代码` 和
`CS0246 未能找到类型或命名空间名 HalconDotNet/Basler/DALSA/...`。

根因有三类：

1. **`AllowUnsafeBlocks` 只写在 Release 配置里**
   `DevMgmt.Cameras`、`DevMgmt.Light`、`Plugin.DefectCoat`、`Plugin.TemplateMatch`、
   `Plugin.CombineLineCross`、`Plugin.ReusableMeasureDetect` 六个工程，Debug 配置缺这一项，
   导致所有 `unsafe` / P/Invoke 代码在 Debug 下编译失败。已补到 Debug 配置。
2. **`HintPath` 指向别的电脑/别的目录树**（从其他解决方案复制粘贴的残留）
   - `..\..\..\combine\DLL\...`（多跳了一级，实际解析到 `D:\combine\DLL`）
   - `..\..\..\..\宽幅打孔新方案1107\...\Mef_VisionFrame\bin\Release\CommunityToolkit.Mvvm.dll`
   - `D:\BaiduNetdiskDownload\宽幅打孔新方案1107\...\halcondotnetxl.dll`、`...\LogTool.dll`
   - `..\..\..\ProcessWideHoleLaser原版测试突然出问题，暂时排查不到原因\Frame_Core\bin\Release\halcondotnetxl.dll`
   全部改回仓库内相对路径；`Frame_Core/FrameCommunity/LogTool` 这类项目间引用改为 `ProjectReference`。
3. **生成后复制原生库无条件执行**
   `Plugin.DefectCoat` 复制 `DefectRuleClassifier\bin\x64\Debug\OpenCvSharpExtern.dll`，
   但 Debug 下该文件实际落在 `bin\x64\Debug\dll\x64\`，根目录没有 → `MSB3030` 直接让整个构建失败。
   已加 `Exists()` 条件并兼容 `dll\x64\` 子目录，同时补上对 `DefectRuleClassifier` 的工程引用。

顺带修正：`Plugin.TemplateMatch`、`Plugin.CombineLineCross`、`Plugin.FindMark` 的 Debug
`OutputPath` 原本输出到各自 `bin\Debug`，运行期根本扫不到；已统一到
`..\Mef_VisionFrame\bin\Debug\Plugins\`。

## 4. 终端故障：Cursor Agent 的 PowerShell 包装脚本被改写

### 现象

Cursor 的 Agent 终端（`Shell` 工具）所有命令都在执行前失败：

```
所在位置 C:\Users\<user>\AppData\Local\Temp\ps-script-<guid>.ps1:8 字符: 4124
表达式或语句中包含意外的标记")"
```

报错位置固定在同一行号/字符位置，并夹带 `?/?C?.?jZ{?|?Y?*S\` 之类乱码。
同一条命令偶尔第一次能跑，之后全部失败；手工开命令行、VS 编译都完全正常。

### 证据

把那个 ps1 转储出来看：

```bat
certutil -encodehex -f "%LOCALAPPDATA%\Temp\ps-script-<guid>.ps1" dump_ps.txt
```

内容形如：

```
0000  ef bb bf 0a 0a 74 72 79 ...   .....try { [Cons
0100  20 7d 0a 0a 0a ef bf bd ef  bf bd 00 00 00 00    }..............
0110  00 00 ... 00                 （约数万个 00）
f7c0  6d 69 6e 67 20 22 66 69 6e  ...  ming "finalize".
f860  54 5f 43 4f 44 45 0a        ...  T_CODE.
```

- 文件开头是**正常的 UTF-8 PowerShell 脚本**（BOM + `try { [Console]::OutputEncoding ...`）。
- 中间出现 `ef bf bd`（U+FFFD 替换字符）+ 大段 `00`（NUL），脚本内容被抹掉。
- 末尾又恢复成正常文本（`Dump-PowerShellState ... exit $COMMAND_EXIT_CODE`）。

`U+FFFD` 大量出现意味着"有人把这个文件按错误的编码读进来、再按 UTF-8 写回去"。
这是安全软件/文件加密客户端（DLP、杀软）做透明扫描/加密时的典型破坏方式，
不是 Cursor 的脚本模板问题，也不是 PowerShell 语法问题：**磁盘上的文件已经坏了**。

### 根治（需要 IT / 安全软件管理员）

任选其一：

1. 把 `Cursor.exe`（以及它派生的 `powershell.exe`）加入安全软件/加密客户端白名单；
2. 或者把 `*.ps1` / `*.cmd` 文件类型排除在实时扫描 / 透明加密策略之外；
3. 或者把 Cursor 升级到最新版（若怀疑是沙箱 sidecar 的编码问题）。

> **已排除的方案**：把 Cursor 的 `TEMP` 换到别的目录**无效**。2026-10-29 实测把 TEMP 指到
> `D:\CursorTemp` 并重启 Cursor 后，`ps-script-*.ps1` 依然在**同一个偏移**（第 8 行、字符 4095）
> 出现 `ef bf bd` + 大段 `00`。说明改写者是按**进程/文件类型**生效，不按目录；
> 该方案只改变文件落点，不解决问题。

### 方案 3 的实测结果：无效（脚本保留，仅供实验）

当时准备的东西仍在本机（不影响系统，可留可删）：

| 文件 | 用途 |
|---|---|
| `D:\CursorTemp\` | Cursor 专用 TEMP/TMP，Agent 的 `ps-script-*.ps1` 会落在这里 |
| `D:\CursorTemp\restart-cursor.cmd` | 强制关闭 Cursor 后用独立 TEMP 重启 |
| `D:\CursorTemp\launch-cursor.cmd` | 只在 Cursor 未运行时启动 |

实测结论：**TEMP 迁移不解决问题**，日常用普通方式（开始菜单/任务栏）启动 Cursor 即可，
不必再用这两个脚本。

### 间歇性特征（2026-10-29 实测）

重启 Cursor 后连续 5 次调用 `Shell`：2 次拿到完整脚本（其中一次是正常的 PowerShell 语法报错，
说明脚本是好的），3 次在被改写的中点（字符 4095）中断。规律是"刚启动的少数几次容易成功，
之后基本都是坏的"，像是实时扫描器介入的竞态。

因此约定：**不要因为某条命令偶然成功就认为已修复**；编译这类耗时操作一律用
`build_debug.bat` 走原生命令行。

### 临时处置（当前可用）

编译器本身没问题，绕过 Agent 终端即可：

1. 打开 **x64 Native Tools Command Prompt for VS**；
2. 进入仓库（避免手输中文路径）：

```bat
for /d %i in (D:\*) do @for /d %j in ("%i\*") do @if exist "%j\combine\Mef_VisionFrame.sln" cd /d "%j\combine"
```

3. `build_debug.bat`，然后用工具读 `build_debug.log`。

同一套处置已经写进 `.cursor/rules/build-and-terminal.mdc`，后续任何 Agent 会话遇到
同样的报错会直接切到原生命令行，不再反复重试。

### 快速自检

```bat
:: 在原生命令行里执行，若输出 ok 说明文件系统正常
cmd /c echo ok
:: 检查某个 ps1 是否被改写（有 ef bf bd + 大段 00 即中招）
certutil -encodehex -f "<path>\ps-script-xxx.ps1" dump_ps.txt
```

## 5. Debug 运行目录缺少原生库（DllNotFoundException）

### 现象

VS 里 Debug 启动后，主窗体加载时崩溃：

```
System.DllNotFoundException: 无法加载 DLL“IOC0640.dll”: 找不到指定的模块。 (0x8007007E)
   在 ControlBoard.板卡库.IOC0640.ioc_config_intbitmode(...)
   在 ControlBoard.板卡类型工具.ControlIOC0640.Config_Intbitmode(...)   ControlBoard640.cs:60
   在 Mef_VisionFrame.Server_DieCuttingCut..ctor(...)                  Server_DieCuttingCut.cs:118
   在 Mef_VisionFrame.Form_Main.Form_Main_Load(...)                    Form_Main.cs:113
```

### 原因

`Mef_VisionFrame\bin\Release` 是历史遗留的“整包部署目录”，除了编译产物还手工放了 22 个 x64 原生库
（Halcon、OpenCV、控制卡、相机/光源 SDK 等）。`Mef_VisionFrame\bin\Debug` 只有 msbuild 生成的文件，
从来没有这些原生库；代码里 `[DllImport("IOC0640.dll")]` 只按文件名加载，于是 Debug 一跑就找不到。

### 处置

把缺的原生库从 Release 拷到 Debug（只拷 x64 的；`bin/` 已被 `.gitignore` 忽略，属本机行为）：

```powershell
cd D:\项目\模切项目\combine
$rel='Mef_VisionFrame\bin\Release'; $dbg='Mef_VisionFrame\bin\Debug'
'ClassifyCPU.dll','CSTControllerDll.dll','cudart64_110.dll','cudnn64_8.dll','ecat_config.dll',
'ecat_master.dll','Ecfg_parser.dll','Glink500.dll','GoSdk.dll','gt_rn.dll','gts.dll','gxn.dll',
'halcon.dll','halconc.dll','halconxl.dll','hcanvas.dll','IOC0640.dll','jsoncpp.dll','kApi.dll',
'LAFunc.dll','opencv_world451.dll','OPTController.dll' |
  ForEach-Object { Copy-Item (Join-Path $rel $_) (Join-Path $dbg $_) -Force }
```

注意事项：

- **不要**复制 `libSkiaSharp.dll`、`halcondotnet.dll`：Release 根目录这两个是 **x86** 版，
  x64 程序应使用 `bin\Debug\x64\libSkiaSharp.dll` 和 `halcondotnetxl.dll`，否则报 `BadImageFormatException`。
- `GoSdk.dll` 单独 `LoadLibrary` 仍返回 126（还缺它的伴生 DLL），只有用 GoSdk 相机时才需要补。
- “清理/重新生成”不会删掉这些手工补的文件（它们不在 `obj\Debug\*.FileListAbsolute.txt` 里）；
  但换机器或重新克隆仓库时要再补一次。生产运行仍以 `bin\Release` 整包为准。
